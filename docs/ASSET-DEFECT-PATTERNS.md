# 可复用资产：回归方法与缺陷模式库

> 来源：FileLens 1.4.2 全量回归（64 项清单 / 29 轮 / 抓到 12 个缺陷）。
> 结论先行：**这 12 个缺陷里没有一个崩溃**。全部是"看起来做了、其实没做"或"位置不对、点不到"。
> 崩渍容易发现，这类才不会。所以下面这些模式值得抄。

---

## 第一部分：12 个缺陷模式

每条都给出「现象 / 为什么容易漏 / 怎么检出 / 修法方向」。**模式名是我起的，便于在别的项目里对照。**

### M1 能力对称性缺失（F1、F5）

**现象**：批量删除有撤销条，单条删除没有；或者反过来。
**为什么容易漏**：两条代码路径分开写，先做了一条，另一条照抄时漏掉一个调用。
**检出**：把所有"批量/单条"成对的操作列成表，逐对检查是否都具备：撤销、确认框、失败提示、刷新。
**修法**：把公共收尾（记 batch、弹撤销条、刷新）抽成一个函数，两条路径都调它。

### M2 浮层 z 序错 + 触摸穿透（F2、F7，同类复发两次）

**现象**：撤销条/Snackbar 弹在底部，被底部导航栏压住；**点它反而切到了别的 Tab**。
**为什么容易漏**：视觉上能看到（半透明能透出字），所以"看起来在"，但点击落到了下层控件。
**检出**：浮层显示时，用 `uiautomator`/注入读出浮层与底栏的 bounds，判断是否重叠；再实际点一下浮层区域，看是否触发了下层动作。
**修法**：**不要靠调 margin 躲**——每个页面底部布局都不同，躲了这个撞那个。改成独立窗口层（根容器最后一个 child，或 PopupWindow），并且 `isClickable = true` 吃掉触摸。

> 这条复发两次的教训：**位置问题要用层级解决，不要用坐标解决。**

### M3 缓存签名挡住强制刷新（F3）

**现象**：删了文件，列表里还在。
**为什么容易漏**：`refresh()` 内部有个"查询签名没变就跳过"的优化，删除不改变查询条件 → 签名不变 → 不重查。
**检出**：任何"数据变了但列表没变"的现象，先查那条路径走的是 `refresh()` 还是"强制刷新"版本。
**修法**：数据变更后的刷新走 `refreshNow()`（绕过签名）；或者让签名包含数据版本号。
**附带风险**：改这里时容易反过来把"索引未就绪"的空态也绕过（见 M4）。

### M4 加载态与空态混为一谈（F4）

**现象**：App 刚启动、索引还没加载完，搜一个存在的文件 → 显示"没有这个文件"。
**为什么容易漏**：功能测试都在"数据已就绪"状态下做，这个窗口只有几百毫秒。
**检出**：冷启动后**立刻**操作（<1s），不要等页面稳定。所有依赖索引的页面都要试。
**修法**：引入明确的 ready 状态；未就绪时显示"正在载入索引…"，就绪后**自动重跑当前查询**。
**判断 ready 的依据**要可靠：不能只看一个布尔，要看数据本身（如 `count > 1`）。

### M5 副作用函数夹带导航（F8）

**现象**：点"撤销"，文件恢复了，但**用户被弹到另一个页面并打开了覆盖层**。
**为什么容易漏**：功能本身是对的（文件确实回来了），只有"在哪"不对。
**检出**：每个"用户触发的小动作"执行后，**断言当前页面没变**（`assert-page`）。这类断言几乎没人写。
**根因**：撤销后调了 `startScan()`，而 `startScan()` 里有 `selectTab(0)` + `showTreeOverlay()` —— 一个"刷新"函数夹带了导航副作用。
**修法**：**刷新函数只准刷新**。要导航由调用方显式决定。局部恢复数据比全量重扫好。

### M6 派生态不跟随源数据（F9）

**现象**：撤销了删除，文件回到磁盘，但"重复文件"页显示 0 组。
**为什么容易漏**：源数据（文件系统）是对的，只是派生态（分组结果）没重算。
**检出**：每个"缓存/派生/聚合"的展示，在源数据变更后都要对一次账。
**修法**：源数据变更 → 明确让派生态失效并重算；开销大就先显示"重新计算中"，不要显示错误结果。

### M7 按钮语义与实现不一致（F10）

**现象**："重新扫描"按钮，在扫描进行中点击 → 只是把扫描**取消**了，什么都不做。
**为什么容易漏**：正常路径（扫描结束后点）完全正确；只有"扫描中再点"这一种状态是错的。
**检出**：**每个按钮都要在"它自己正在执行时"再点一次**。这是最容易漏的状态组合。
**根因**：`if (scanner != null) { cancelScan(); return }` —— 把"重入保护"当成了"取消"。
**修法**：要么取消后立刻重开（注意等旧线程退出），要么按钮置灰并给出反馈。**不许静默什么都不做。**

### M8 索引范围包含了不该含的目录（F12）

**现象**：搜 `DCIM/` 返回了已删除、躺在回收站里的文件（回收站真实路径里含 `DCIM/`）。
**为什么容易漏**：路径是"对的"，只是那个路径不在用户语义范围内。
**检出**：搜索/统计类功能，要拿"内部目录"（回收站、缓存、临时目录）去搜一次，看会不会被命中。
**修法**：扫描阶段就排除内部目录（比在每个查询里过滤更彻底，顺带修掉统计虚高）。

### M9 双因缺陷：两个独立 bug 叠加（F11）

**现象**：树图下钻后，点面包屑回不到根。
**为什么难**：**两个独立原因同时存在**——
- 原因 A：返回按钮热区（44dp 方块）与第一段面包屑坐标重叠，且 `hit()` 里返回按钮优先级更高 → 点面包屑被返回按钮抢了
- 原因 B：`showRoot()` 只更新了 `treemap.setRoot()`，**没调列表刷新** → 数据层根本没变

**修了 A 仍然不通**，因为 B 才是主因。
**检出**：**用"绕过 UI 直接调业务函数"的方式验证**（如 `--es flTap <id>` 直接调 `showRoot(0)`）。
- 直接调也不行 → 问题在被调函数，不在命中区
- 直接调可以 → 问题在命中区

**这一条是整轮回归最大的方法论收获**：不确定"点不到"还是"点了没用"时，**先绕过 UI 调一次**，能立刻把搜索空间砍一半。

### M10 主线程长任务（不属于功能 bug，但影响体验）

**现象**：首帧出来了，紧接着卡 400–500ms。
**检出**：给"启动"打分段点，不要只测总时长。本例的分解：
```
Application       67–130ms
onCreate          917–1028ms   （构建 5 个页面）
onResume          332–398ms    （含断点重算）
→ 首次布局/绘制    到 1567–1639ms
快照回调(主线程)   2043–2122ms  ← 首帧后还有 ~470ms
```
**关键发现**：`am start -W` 的总时长被**首帧之后**的主线程任务拉长了，所以"优化首帧"和"优化总时长"是两件事。
**修法**：回调里的重活挪走 / 只刷当前可见页，其它页标 dirty 等切过去再刷。

### M11 状态残留导致测试误判（非 App 缺陷）

**现象**：重装 App 后所有删除测试都失败，报"移动失败，文件未删除"。
**真因**：`MANAGE_EXTERNAL_STORAGE` 在重装后回到 `default`。
**教训**：**重装后必须重新授权**，否则会把环境问题误判成 App bug，浪费整轮。

### M12 环境能力差异（非 App 缺陷）

模拟器测不了的：摄像头扫码、系统回收站、真实存储 IO 特性、动效流畅度。
**处理原则**：一律标 `BLOCKED(具体原因)`，**不要用"看起来正常"糊过去**，也不要为了凑通过率改测试步骤。

## 第二部分：方法论（比缺陷清单更可迁移）

### 1. 先量再改

冷启动慢，第一反应是"快照反序列化"——去读代码发现快照是紧凑二进制 + 批量 ByteBuffer，注释写着"10 万节点目标 ≤300ms"，压根没有反射。真凶是别处。

**规则：任何性能判断，先加时间戳，再动手。**

### 2. 代码核对不能替代实跑

有一版代码改对了（命中优先级 + 收窄热区，逐行核对无误），但界面就是不通——因为还有第二个原因。**"代码看着对"最多算 `FIXED-UNVERIFIED`，不算通过。**

### 3. 区分"我点错了"和"App 坏了"

整轮里我误判过 4 次：没滚到真底就说"底部内容不可达"；假设屏宽密度算错一倍；用 CDP 设计原生输入框的方案；断言 App 大量用全屏 Dialog。

**防误判的三条**：
- 判断"滚不到底"前，先确认 `scrollTop + innerHeight >= scrollHeight - 2`
- 判断"尺寸不对"前，先 `wm size` + `wm density` 算，不要凭分辨率推
- 判断"点不动"前，先用"绕过 UI 直接调函数"验证（见 M9）

### 4. 证据等级要分清楚

| 等级 | 含义 | 允许写成 |
|---|---|---|
| 实跑通过 | 有截图/logcat/md5 佐证 | `PASS` |
| 修复后重跑通过 | 同上，且是修复后 | `PASS(修复后)` |
| 代码核对通过 | 只是读代码确认 | `FIXED-UNVERIFIED` |
| 环境不支持 | — | `BLOCKED(原因)` |
| 没跑 | — | `NOT RUN` |

**不许把 3 写成 1 或 2。** 这一条比测出多少 bug 更重要。

### 5. 边测边落盘

60+ 条清单不可能一轮跑完。**每完成一组就写进结果文档并 commit**，跑不完就如实写"停在第 X 条"。攒到最后一次性写 = 赌不会中断。

### 6. 时间盒

单个条目卡住超过 15 分钟就记 `BLOCKED` 换下一条。整轮的价值是覆盖面和缺陷数，不是把某一条磨通。

### 7. 工具的瓶颈优先解决

回归前 15 轮，大半时间花在"点不到目标控件"上。加了 App 内 Debug 跳转 + 控制点导出之后，同样的事 20 秒完成。

**当测试变慢时，先怀疑工具，不要硬扛。**

## 第三部分：给下一个项目的最小清单

写代码时就顺手加上，能省掉后期一大半麻烦：

1. **每个"刷新"函数保持纯度** —— 只刷新，不导航、不改 Tab、不弹层
2. **每个浮层显式吃掉触摸** —— `isClickable = true`，并且放在层级最高处
3. **加载态与空态分开** —— 有"正在载入"这个第三种状态
4. **每个按钮都在"自己正在跑"时再点一次** —— 这是最容易漏的状态组合
5. **撤销/恢复后不要全量重扫** —— 局部恢复数据 + 只刷当前页
6. **内部目录（回收站/缓存）在扫描阶段就排除**
7. **Debug 跳转入口 + 控制点导出，从第一版就加**
8. **启动分段打点，不要只测总时长**
