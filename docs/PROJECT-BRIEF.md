# FileLens（SpaceLens）项目说明 —— 供外部技术评审

> 写这份文档的用途：把项目现状完整交代给一个**没有上下文**的强模型，请它给出架构与产品层面的判断。
> 所有数字与结论都来自真实代码与实测，不是估计。文档末尾有明确的提问清单。

---

## 一、这是什么

一个**单机安卓文件管理器 / 空间清理工具**，包名 `com.hu4222.filelens`，由一个人（含 AI 协作）开发，累计约 12 个版本迭代到 1.4.2。

核心卖点有三个：

1. **空间可视化**：矩形树图（treemap）显示磁盘占用，可逐层下钻
2. **局域网传输**：手机开一个 HTTP 服务，电脑用浏览器访问即可浏览/下载手机文件（反向也能传）
3. **安全删除**：所有删除先进应用内回收站，可撤销、可恢复，30 天自动清理

**当前状态**：1.4.2，APK 5.04 MB，`minSdk 26 / targetSdk 34`，仅在 Android 14 模拟器（API 34）上验证过，**未在真机做完整验收，无正式签名（仍用 debug keystore），未上架**。

---

## 二、目标用户与场景

**自用为主**。典型场景：

- 手机存储快满了，想知道「到底什么占了 190GB」
- 想一次性找出重复照片/大文件
- 想不用数据线，在同一个 Wi-Fi 下用电脑浏览器把手机里的文件拿下来
- 删东西时怕删错，希望有后悔药

**不是**面向大众市场的产品（没有引导、没有账号、没有云同步）。

## 三、技术架构

### 3.1 分层

```
┌──────────────────────────────────────────────────────┐
│ 原生 UI 层（Kotlin，全部自绘）                        │
│  59 个 .kt 文件 / 17,268 行                          │
│  空间页(Canvas 树图) 搜索 清理 传输 设置 预览 回收站   │
├──────────────────────────────────────────────────────┤
│ 传输页 = WebView + 内置网页（3,925 行 js/css/html）    │
│  网页资源在 assets/www/，运行时通过 JS 注入改行为      │
├──────────────────────────────────────────────────────┤
│ 核心引擎（纯 Kotlin，无 Android UI 依赖）             │
│  Scanner(DFS 扫描) NodeStore(扁平数组索引树)          │
│  Duplicates(SHA-256 去重) GarbageAdvisor Health      │
│  Trash(回收站) SnapshotStore(快照) FileOps(文件操作)  │
│  CacheCleaner(Shizuku 可选)                          │
├──────────────────────────────────────────────────────┤
│ HttpServer（NanoHTTPD 手写） / TransferService        │
└──────────────────────────────────────────────────────┘
```

### 3.2 几个非常规的技术选择（都有理由，见第六节）

| 选择 | 替代方案 | 为什么这么选 |
|---|---|---|
| **UI 全部 Canvas 自绘**（不用 Compose，几乎不用 XML） | Compose / XML | 想要完全一致的视觉与动画控制；代价是可访问性差、UI 自动化极难 |
| **`NodeStore` 用扁平数组 + int 索引** | 对象树 | 十万级节点，对象树 GC 压力大；扁平数组内存小、遍历快 |
| **传输页用 WebView 而非原生** | 全原生 | 网页端代码复用自既有的 DropLink 项目，一次写好电脑手机通用 |
| **伪玻璃**（半透明+高光+内阴影），不做真模糊 | RenderEffect / 第三方库 | Android View 体系没有等价于 iOS `UIVisualEffectView` 的能力；`RenderEffect` 模糊的是控件自身不是背后内容 |

### 3.3 关键数据结构

`NodeStore`：所有节点放在扁平数组里，每个节点存 `name / parent / firstChild / nextSibling / size / flags / mtime`，用 int 索引互相引用。树操作靠修补索引完成（`renameNode / moveNode / addDir / restoreNode`），**不重建整棵树**。

`SnapshotStore`：扫描结果序列化落盘，冷启动先加载快照再决定是否重扫。

### 3.4 权限模型

依赖 `MANAGE_EXTERNAL_STORAGE`（所有文件访问）。Shizuku 是**可选项**，只用于清理其他应用的缓存目录（未安装时相关 UI 整块隐藏）。

## 六、关键设计决策（这些是"理由"，不是"实现"）

| 编号 | 决定 | 否决了什么 | 代价 |
|---|---|---|---|
| D-01 | 传输保留配对码但走挑战-应答（`SHA256(pin+":"+nonce)`），握手后明文 | 完全开放 / HTTPS 自签证书 / 全链路加密 | 只防偷看配对码，不防嗅探内容 |
| D-02 | 玻璃质感用伪玻璃（半透明+高光+内阴影+0.5dp 亮边+3% 噪点） | 真模糊（`RenderEffect` 在 View 体系里模糊的是控件自己）；Haze 等库 | 高对比内容背后会"透字"，只能靠提高不透明度补偿 |
| D-03 | 照片清理做「打分 + 原型检索」而不是训练模型 | 训练分类模型 | 准确率靠规则，不靠学习 |
| D-04 | 不删除、不替换原有组件（除非功能完全不可用） | 推倒重写 | 历史遗留的重复实现会留着 |
| D-05 | 签名固定不再更换 | —— | 换 keystore 会导致覆盖安装被拒、要卸载重装并丢权限 |
| D-06 | **一次只交付一个可验收的版本** | 一个大版本塞多个功能 | 迭代慢，但每次改动可回滚 |
| D-07 | 树图**视觉面积与真实字节解耦**（小到看不见的项有最小面积） | 严格按比例 | 视觉上会读不出"这个文件其实很小" |
| D-08 | **网页资源零改动**，所有行为改动走运行时 JS 注入 | 直接改 `assets/www/` | 注入代码分散在 Kotlin 里，调试更绕 |

---

## 七、硬约束（违反即回退）

1. **不许改 `app/src/main/assets/www/`** ——网页资源一个字节都不动，行为改动必须走运行时注入
2. **`HttpServer.kt` 里 `deleteRecursively` 必须为 0** ——浏览器端不能触发递归删除
3. 删除一律走 `Trash`，不允许直删
4. 不引入第三方依赖（现有 10 个：core-ktx、shizuku×3、zxing、activity、camerax×4）
5. Debug 脚手架（`flPage` / `flCleanSeg` / `flDumpCounts` 跳转入口）必须在 `BuildConfig.DEBUG` 内

## 八、已知缺陷与遗留风险

### 8.1 已修（1.4.2 回归中抓到的 9 个）

| 编号 | 问题 | 性质 |
|---|---|---|
| F1 | 单条删除没有撤销入口（只有批量有） | 数据风险 |
| F2 | 撤销条被底栏遮挡，**点它会切到别的 Tab** | 数据风险 |
| F3 | 删除后搜索结果不刷新 | 一致性 |
| F4 | 索引未就绪时搜出「没有这个文件」——假空 | 误导 |
| F5 | 批量删除没接撤销 | 数据风险 |
| **F8** | **点撤销把用户弹回空间页并打开树图** | 体验断裂 |
| F9 | 撤销后清理页显示「0 组」但文件在磁盘 | 一致性 |
| **F10** | **扫描中点「重新扫描」只是取消扫描，什么都不做** | 静默失败 |
| F12 | 路径搜索会命中回收站里的文件 | 误导 |

**F8 和 F10 的共同点**：不是崩溃，而是"看起来做了、其实没做"。这类问题比崩溃更伤信任。

### 8.2 未修

**F11 树图导航** —— 这是当前最大问题：
- 现象：下钻进子目录后，点面包屑「内部存储」回不到根；点返回箭头也无反应
- 根因（已确认）：返回按钮的热区（44dp 方块）与第一段面包屑在坐标上重叠，而 `hit()` 里返回按钮优先级更高
- 已做：把面包屑判断提到返回按钮之前，并把返回热区收进卡片内（代码层已核对正确）
- **未解决的部分**：树图整体存在"难以稳定进入目标目录"的问题，导致该修复无法在界面上验收
- 连带阻塞：`T→Tx` 前缀边界、新建文件夹这两项无法验证

### 8.3 未验证清单

42 关服务不自动重启、51 预览视频/文本/PDF、R6 原目录不可写恢复、57 新建文件夹、`T→Tx` 边界

## 九、当前最大的痛点（技术层面）

### 9.1 UI 自动化几乎不可行（这是最贵的成本）

因为 **UI 全部 Canvas 自绘**：
- `uiautomator dump` 拿不到文字节点（只有 4.6KB 空壳）
- 只能靠截图 + 坐标点击，而坐标在不同启动状态下会偏
- 一条测试平均要试 3–5 次才能进到目标页

**目前的缓解手段**：在 App 里加了 Debug-only 的跳转入口（`--es flPage clean` 直接跳清理页、`--es flCleanSeg 2` 直接切分段、`--ez flDumpCounts` 把各模块计数打到 logcat）。加了之后测试效率提升明显，但这是"给测试开后门"，不是根治。

**结果**：64 项回归清单，用了 29 轮才跑到 60 项，且其中 5 项最终判定为"无法在界面验证"。

### 9.2 冷启动 3.7 秒偏慢

| 阶段 | 时间 |
|---|---|
| 冷启动到首屏可交互 | 3,551–3,911 ms |
| 全盘扫描（9,118 文件） | 4,235 ms |

冷启动大概率卡在快照加载（`SnapshotStore`）。用户能接受，但明显偏慢。

### 9.3 单文件应用已经 1.7 万行

`MainActivity.kt` 单文件超过 1,200 行，承担了页面组装、权限、扫描编排、删除、覆盖层、Debug 入口等职责。功能继续加会失控。

## 十、想请你判断的问题

请针对以下问题给具体建议，不要泛泛而谈"建议重构"或"建议上 Compose"：

### A. 可测试性
Canvas 自绘 UI 导致自动化回归成本极高（29 轮才跑 60 项）。在**不重写 UI** 的前提下，有没有比"加 Debug 跳转后门"更系统的做法？

### B. 树图导航该怎么修
面包屑/返回箭头在坐标上重叠的问题，用"调命中优先级 + 收窄热区"是否足够？还是应该改成有明确布局的容器（比如把面包屑做成一行真实的 View 而不是 Canvas 里画的矩形）？后者会不会破坏现有的视觉一致性？

### C. 下一个功能该做哪个
候选：
1. 定时自动清理（WorkManager，每周扫一次推通知）
2. 原生文件操作扩展（复制/压缩/解压）
3. 重复**照片**检测（感知哈希，现在的 SHA-256 认不出"同一张图不同尺寸"）
4. SAF 自选目录（不依赖 MANAGE_EXTERNAL_STORAGE）

从"对用户价值 / 实现风险 / 与现有架构契合度"三个维度排序，并说明理由。注意：删除链路刚经历 9 个 bug 的修复，是否应该先稳住再上新功能？

### D. 冷启动优化该从哪下手
3.7 秒。怀疑瓶颈在快照加载。在"不动架构"的前提下，第一步应该测什么、改什么？

### E. MainActivity 该不该拆，怎么拆
1,200 行、职责过多。如果拆，按什么边界拆最不容易引入回归？考虑到这个项目每次改动都要真机/模拟器验收，拆分的收益是否值得风险？

### F. 该不该继续用 MANAGE_EXTERNAL_STORAGE
Google Play 对该权限审核极严。如果目标是"自用 + 小范围分发"，还需要考虑迁移到 SAF 吗？还是这个顾虑可以忽略？
